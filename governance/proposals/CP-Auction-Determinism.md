## 1. Problem statement

EAE-0002 states the test this proposal adopts as its acceptance criterion:

> An implementer MUST be able to build a SIGNET reverse-auction engine from the specification and conformance fixtures alone, without the reference runtime, and obtain byte-equivalent close inputs and the same semantic Award.

At v0.17.1 that is not possible. The deterministic close is *modelled*, partly *tested*, and not *certified*:

- **D-62.** The close is defined over "the same rules over the same bids". Order, supersession, withdrawal, rejection, rounds and eligibility change the result and are not inputs to the definition.
- **D-63.** Step, round completion and the no-improvement close are under-specified.
- **D-64.** `earliest-bid` has no authoritative order. The checker breaks ties by directory listing order.
- **D-65.** `random-seeded` requires a published seed that `rules` cannot carry.
- **D-66.** `split` contradicts the single-winner model.
- **D-67.** Amounts have no precision or arithmetic rule.
- **D-68.** The checker tests A1..A3 and none of the rule parameters, and has no replay.
- **D-69.** The schema admits combinations whose semantics are contradictory (Dutch, direction, lots, Award linkage).
- **D-70.** The event hash is defined only in code.
- **D-71.** Chain scope is per subject in the adapter contract and global in the auction runtime.

The remedy is a hardening pass, not a redesign: one mechanism, reverse multi-round, is specified completely enough to be implemented from the text and fixtures; every other combination is reserved with its reason; and the chain and hash the close depends on are defined normatively.

## 2. Proposal

Normative keywords per RFC 2119. The profile (§2.8) is what certification tests.

### 2.1 Chain scope and the event hash (D-70, D-71)

**Hash (all Event chains).** `previousEventHash` is the string `sha256:` followed by the lowercase hexadecimal SHA-256 digest of the UTF-8 bytes of the RFC 8785 (JSON Canonicalization Scheme) serialisation of the prior `Event`, as recorded, including that Event's own `previousEventHash` where present and excluding nothing. The value is 71 characters and matches `^sha256:[0-9a-f]{64}$`. An `Event` that is not I-JSON (RFC 7493: for example a string containing a lone surrogate, or a duplicated member name) has no defined hash and is invalid.

This names the algorithm the tooling already implements. Checked on 15 September 2026 against an RFC 8785 implementation written from the RFC: all 2,018 JSON sub-documents in the 100 tracked `.json` and `.jsonld` files serialise identically under `conformance/runner/lib.js` `stableStringify`, and all 24 events generated by the three demonstrations re-hash identically. The only divergence is non-I-JSON input, which this section makes invalid. `docs/specification.md` (`Event.previousEventHash`) and `conformance/adapter/adapter-contract.md` carry the definition; `runner/lib.js` becomes an implementation of it rather than its source.

**Chain scope (auctions).** An `Auction` has exactly one chain. Its first event is `auction.scheduled`, which carries no `previousEventHash`. Every later event whose `subject` is the Auction or one of its Bids is appended to that chain, and its `previousEventHash` is the hash of the immediately preceding event on the chain. An event on a Bid of an Auction MUST NOT appear on any other chain. The per-subject rule in the adapter contract continues to govern every other object; this section is the auction's exception to it, stated in the adapter contract.

**Chain position** is an event's zero-based index on its Auction's chain. It is the authoritative order for every rule in this proposal.

**Chain-time** is an event's `timestamp` as recorded. On an Auction chain every `timestamp` MUST be a UTC date-time with the `Z` designator, and timestamps MUST be non-decreasing in chain position. *(CP decision, §7.1.)* Chain-time decides admission at a time boundary (§2.3.5) and nothing else; it never orders events.

**Vectors.** `conformance/vectors/event-hash/` publishes three vectors, each an input Event and its expected `previousEventHash` for a successor, in the prefixed form: a minimal event; an event with a payload; an event with a nested `Identifier`, non-ASCII strings and member names whose UTF-16 order differs from code-point order. An implementation that computes the digest correctly and omits the prefix fails a vector.

### 2.2 The deterministic close (D-62)

The close of an Auction is a deterministic function of:

1. the Auction as frozen at `auction.started` (§2.3.1);
2. the Auction's chain, in chain position order;
3. the immutable inputs the chain references, each pinned by hash: the `SupplierQualification` evaluated for each standing bid (§2.3.7).

**Standing-bid projection.** Fold over the chain in position order, maintaining a map from bidder to standing Bid:

- a `bid.placed` that is valid under §2.3 sets the bidder's standing Bid to the placed Bid;
- a `bid.withdrawn` or `bid.rejected` for the bidder's standing Bid clears it;
- a `bid.placed` that is not valid under §2.3 leaves the map unchanged, and MUST be followed, before any other `bid.placed`, by `bid.rejected` for that Bid carrying the reason (§2.3.9).

When a valid placement replaces a standing Bid, a `bid.superseded` event for the replaced Bid, whose payload `supersededBy` names the new Bid, MUST follow before any other `bid.placed`. The projection does not read `bid.superseded`; the checker verifies it names the Bid the projection replaced. `Bid.status` stored on an object is a projection and MUST equal what the chain yields (state model S-2).

**Close inputs record.** The close produces one JSON object, the close inputs record:

```json
{
  "auction": { "id": { "scheme": "…", "id": "…" }, "hash": "sha256:…" },
  "precedingEvent": "sha256:…",
  "currency": "EUR",
  "minorUnitExponent": 2,
  "standing": [
    { "bid": { "scheme": "…", "id": "…" }, "bidder": { "scheme": "…", "id": "…" }, "amountMinor": 1080000000, "position": 41 }
  ],
  "eligibility": [
    { "bid": { "scheme": "…", "id": "…" }, "qualification": "sha256:…", "eligible": true }
  ],
  "tieBreak": { "rule": "earliest-bid" },
  "result": { "bid": { "scheme": "…", "id": "…" }, "awardedParty": { "scheme": "…", "id": "…" }, "amountMinor": 1080000000 }
}
```

- `auction.hash` is the §2.1 hash of the frozen Auction. `precedingEvent` is the hash of the last event before `auction.closed`.
- `standing` is sorted by `amountMinor` ascending, then `position` ascending. `eligibility` follows the same order; an ineligible entry carries `reason` (§2.3.7).
- `tieBreak` carries `seed` and `tied` (the tied Bids, in `standing` order) when `random-seeded` was applied, and `tied` alone when `earliest-bid` was applied to a tie.
- `result` is `null` when no standing bid is eligible.

**Close inputs record fields (normative).** The example above is illustrative; this list is the shape. The record is closed: no member other than those listed is permitted, at any level. `Identifier` is core `definitions.schema.json#/definitions/Identifier`. `Hash` is a string matching `^sha256:[0-9a-f]{64}$`, computed as in §2.1 over the named object.

| Field | Type | Required | Content |
|---|---|---|---|
| `auction` | object | yes | Members `id` and `hash` only |
| `auction.id` | `Identifier` | yes | The Auction's `id` |
| `auction.hash` | `Hash` | yes | The frozen Auction (§2.3.1); equals the `auction.started` payload's `auction` |
| `precedingEvent` | `Hash` | yes | The last event before `auction.closed`; equals that event's `previousEventHash` |
| `currency` | string, `^[A-Z]{3}$` | yes | The Auction's single currency (§2.5) |
| `minorUnitExponent` | integer, 0..4 | yes | From the support matrix currency table (§2.6) |
| `standing` | array | yes, may be empty | One entry per standing Bid at close, sorted by `amountMinor` ascending, then `position` ascending |
| `standing[].bid` | `Identifier` | yes | The standing Bid |
| `standing[].bidder` | `Identifier` | yes | `Bid.bidder` |
| `standing[].amountMinor` | integer, 0..2^53 − 1 | yes | §2.5 |
| `standing[].position` | integer ≥ 0 | yes | Chain position of the standing `bid.placed` |
| `eligibility` | array | yes, may be empty | One entry per `standing` entry, same order |
| `eligibility[].bid` | `Identifier` | yes | Equals the `standing` entry's `bid` at the same index |
| `eligibility[].qualification` | `Hash` or `null` | yes | The `SupplierQualification` evaluated; `null` only with reason `no-qualification` or where `requiresQualification` is false or absent |
| `eligibility[].eligible` | boolean | yes | §2.3.7 |
| `eligibility[].reason` | string, a code of `ineligibilityReason.csv` | iff `eligible` is false | §2.3.7 |
| `tieBreak` | object | yes | |
| `tieBreak.rule` | string, `earliest-bid` or `random-seeded` | yes | `rules.tieBreak` |
| `tieBreak.tied` | array of `Identifier` | iff a tie among eligible standing Bids decided the result | The tied Bids, in `standing` order |
| `tieBreak.seed` | string | iff `rule` is `random-seeded` and `tied` is present | `rules.tieBreakSeed` |
| `result` | object or `null` | yes | `null` iff no standing Bid is eligible |
| `result.bid` | `Identifier` | yes when `result` is an object | The winning Bid |
| `result.awardedParty` | `Identifier` | yes when `result` is an object | Equals the winning `standing` entry's `bidder` and `Award.awardedParty` |
| `result.amountMinor` | integer | yes when `result` is an object | Equals the winning entry's `amountMinor`; `Award.value` is its decimal form in `currency` |

PR-C publishes this list as `conformance/rules/auction-close-inputs.schema.json` (Draft-07, no `$id` in the CDM namespace: it is a conformance artifact, not a CDM object), and A4 validates every produced record against it before comparing bytes.

The record is compared as its RFC 8785 serialisation. Two conformant implementations MUST produce byte-identical records and the same `Award.awardedParty` and `Award.value`.

**Anchoring.** The `auction.closed` event's payload carries `{ "closeInputs": "sha256:…" }`, the hash of the record's RFC 8785 serialisation computed as in §2.1. The chain anchors the record; no stored Decision can be changed to disagree with it undetectably.

**Decision and Award.** The close emits a `Decision` (`decisionType: award`) whose `inputs` list the Auction and every Bid in `standing`, as `Identifier`s, and an `Award` whose `sourcingEvent` is the Auction's `sourcingEvent`. `Decision.inputs` does not carry the record's hash or the seed: `Identifier.scheme` is closed to entity-naming schemes, and a hash is not an entity (D-20). The anchored record carries both. When D-20 is resolved, the Committee may add a reference from the Decision; that is recorded in §7 and does not change the record.

### 2.3 Reverse, multi-round mechanism (D-63)

Applies when `auctionType = reverse` and `rules.roundStructure = multi-round`.

1. **States and freezing.** In `scheduled` only `auction.opened` and `auction.cancelled` are admitted. In `open` no `bid.*` or `round.*` event is admitted; participation is recorded by the operator outside the chain. `auction.started` enters `in_progress`; its payload carries `{ "auction": "sha256:…" }`, the §2.1 hash of the Auction with `status` removed, and from that event `id`, `sourcingEvent`, `procuringParty`, `auctionType`, `lots`, `rules`, `eligibility` and `period` MUST NOT change. In `in_progress`, `round.opened`, `round.closed`, `bid.*`, `auction.closed` and `auction.cancelled` are admitted. After `auction.closed`, only `bid.won` for the `result` Bid (at most once) and annotation events are admitted. `closed` is entered from `in_progress` only: the registry's `open → closed` edge is removed, and an Auction that never starts is `cancelled`. *(CP decision, §7.1.)*
2. **Opening bid.** A bidder's first `bid.placed`, or its first after a withdrawal, is valid iff `amountMinor ≤ startPrice` (when present) and `amountMinor ≥ reservePrice` (when present).
3. **Improvement.** A later `bid.placed` from a bidder with a standing Bid is valid iff `amountMinor ≤ standing − minStep` and `amountMinor ≥ reservePrice` (when present). `minStep` binds a bidder's own successive offers, not the gap to the current best; when absent it is one minor unit. *(CP decision, §7.1.)*
4. **Rounds.** `round.opened` with payload `{ "round": n }` and `round.closed` with payload `{ "round": n, "improved": b }` have the Auction as subject. Rounds are numbered from 1 and consecutively; round n+1 opens only after round n closes. A `bid.placed` is admitted only while a round is open, and `Bid.round` MUST equal it (otherwise `round-mismatch`). `improved` is `true` iff at least one valid `bid.placed` occurred in the round; the checker recomputes it.
5. **Close conditions.** `no-improvement`: the Auction closes on the first `round.closed` with `improved = false` and `round ≥ 2`. `max-rounds`: closes on `round.closed` with `round = maxRounds`; `maxRounds` is required. Whatever the close condition, `maxRounds` when present closes the Auction at that round. *(CP decision, §7.1.)* `fixed-time`: a `bid.placed` is admitted iff its chain-time is **≤ `period.endDate`** (inclusive, matching core `Period`); `auction.closed` has chain-time strictly after `period.endDate`, and an open round is closed immediately before it. In every case `auction.closed` is the next event after the event that satisfies the condition, and does not appear otherwise. A `bid.placed` after `auction.closed` is invalid regardless of chain-time. Extending `period.endDate` after `auction.started` is not possible (item 1); close-time extension is reserved (§2.7).
6. **Passing.** No event records a pass. A bidder with no valid `bid.placed` in a round keeps its standing Bid.
7. **Eligibility at close.** Take `standing` in order. For each, evaluate the bidder's `SupplierQualification`, pinned by its §2.1 hash in the record: eligible iff `eligibility.requiresQualification` is false or absent; or the qualification's `status` is `active`, or `conditional` where `minStatus = conditional`; its `validity`, when present, contains the chain-time of `auction.closed`; and every condition is a `valueCap` in the Auction's currency that `amountMinor` does not exceed. The first eligible standing Bid wins, subject to ties (§2.4). An ineligible standing Bid stays in the record with a reason from `ineligibilityReason.csv`: `no-qualification`, `status-below-minimum`, `qualification-expired`, `value-cap-exceeded`, `condition-unsupported`. *(CP decision, §7.1.)* It is not rejected. When none is eligible the Auction closes with `result: null`, no `Award`, and a `Decision` stating so.
8. **Ties.** Eligible standing Bids with equal `amountMinor` resolve by `tieBreak` (§2.4).
9. **Withdrawal and rejection.** `bid.withdrawn` clears the standing Bid; the bidder may place a new opening bid. `bid.rejected` carries `{ "reason": … }` from `bidRejectionReason.csv`: `reserve-breach`, `start-breach`, `step-breach`, `round-mismatch`, `state-breach`, `time-breach`, `ineligible`, `duplicate`, `currency-mismatch`, `precision-breach`. `ineligible` is used at placement only where the operator records that the bidder had no qualification when `requiresQualification` is true; eligibility at close is item 7. A rejected placement never enters the projection, and a valid placement is never rejected.
10. **Duplicates.** A `bid.placed` for a Bid `id` already on the chain is invalid (`duplicate`). Idempotent command handling is an operator concern; the record is not.

### 2.4 Ordering and ties (D-64, D-65, D-66)

- **`earliest-bid`.** The tied Bid whose standing `bid.placed` has the lower chain position wins. `timestamp` is not consulted.
- **`random-seeded`.** `rules.tieBreakSeed` is a non-empty string, required iff `tieBreak = random-seeded`, part of the Auction from `auction.scheduled` and so published before bidding and frozen at `auction.started`. For each tied Bid compute HMAC-SHA-256 with key the UTF-8 bytes of the seed and message the UTF-8 bytes of the bidder's `Identifier.scheme`, a colon, and `Identifier.id`. The lowest output, compared as unsigned big-endian bytes, wins *(CP decision, §7.1.)*; equal outputs fall back to `earliest-bid`. The seed is echoed into the close inputs record (§2.2).
- **`split`.** Stays in the enum for compatibility, is `reserved` in the support matrix, and fails A10.

### 2.5 Money (D-67)

- Every amount in an Auction (`startPrice`, `reservePrice`, `minStep` and every `Bid.value`) MUST share one `currency`, which MUST appear in the support matrix's currency table.
- An amount MUST be non-negative and carry no more fractional digits than the currency's minor-unit exponent. Digits are counted on the RFC 8785 serialisation of the number, so the test does not depend on binary floating point.
- `amountMinor` is the amount scaled by 10^exponent, computed by moving the decimal point in that serialisation, and MUST NOT exceed 2^53 − 1. All rule arithmetic and comparison MUST use `amountMinor` (or an exact decimal type). Implementations MUST NOT use binary floating point for any decision that affects validity, ranking or the close.
- Core `Value.amount` does not change.

### 2.6 Support matrix (D-69)

`conformance/rules/auction-support-matrix.json` holds:

- `combinations`: an array of `{auctionType, roundStructure, closeCondition, tieBreak, identityDisclosure, status, reason?}`, where `status` is `supported` or `reserved` and `reason` is required for `reserved`;
- `currencies`: an array of `{code, minorUnitExponent}`.

This proposal marks exactly one family supported: `reverse` × `multi-round` × {`no-improvement`, `max-rounds`, `fixed-time`} × {`earliest-bid`, `random-seeded`} × {`anonymous-ranks`, `open`}. Every other combination is `reserved` with its reason from §2.7. The initial currency table is EUR, GBP, USD, CHF, SEK, NOK, DKK, PLN (exponent 2) and JPY (exponent 0), and is extended by amendment. *(CP decision, §7.1.)* The checker loads the file; an Auction whose combination or currency is not supported fails A10 with the reason. The extension's documentation lists the matrix generated from the file, not restated in prose.

### 2.7 Reserved capabilities

Each is not certifiable; the condition for unreserving is a proposal that specifies it to the standard of §2.3.

| Capability | Reason reserved |
|---|---|
| `dutch` | A descending clock closed by first acceptance is a different price-formation algorithm from a standing-bid close; choosing a direction does not repair it. The checker's treatment of Dutch as lower-wins is removed |
| `split` | Needs a multi-winner award model; `Award.awardedParty` is single |
| Sealed value | `sealed-until-close` remains an identity-disclosure setting only. Sealing values needs a commitment or envelope mechanism |
| `sealed-bid`, `multi-criteria` | No direction, and for multi-criteria no defined inputs. Preference recorded: a Bid references its Submission and Evaluation inputs by hash rather than duplicating them |
| `english`, `single-round`, `continuous` | Not specified to §2.3's standard |
| Multi-lot | `Bid` cannot address a lot. The profile allows `Auction.lots` of length ≤ 1; one Auction per lot |
| Close-time extension | Anti-sniping is a rules-governed event or nothing; operator-policy extension is prohibited in the profile |
| `rules.direction` | Field name reserved (`lower-wins`, `higher-wins`) for when `sealed-bid` or `multi-criteria` is unreserved. Direction is never inferred from `startPrice` or `reservePrice` |

### 2.8 Profile `auction-platform` v0.2

Requirements restated against §2.1 to §2.7:

- **AP-1** valid objects, including the support matrix and currency table.
- **AP-2** deterministic close by replay: A4 to A14 against the published fixtures, with byte-identical close inputs records.
- **AP-3** tamper-evident record: one chain per Auction, hashed per §2.1, passing the vectors.
- **AP-4** unchanged: record completeness, not enforcement.
- **AP-5** unchanged, still provisional on the identity extension.
- **AP-6** supported combination and currency only.
- **AP-7** `Auction.sourcingEvent` is required, and `lots` has at most one entry. The requirement is the profile's; the schema is unchanged (§7).

The certification statement carries the acceptance criterion from §1.

## 3. Schema changes

- `schema/auction.schema.json`: `rules.tieBreakSeed` (`string`, `minLength: 1`); `if tieBreak = random-seeded then required tieBreakSeed` and `if closeCondition = max-rounds then required maxRounds` (Draft-07 `if`/`then`, valid in 2020-12 unchanged). `description` updates for `minStep`, `reservePrice`, `closeCondition`, `tieBreak`. No `$id` change; namespace stays `v0.1`.
- `schema/event.schema.json` (core): `previousEventHash` gains `pattern: ^sha256:[0-9a-f]{64}$`. No pattern exists at v0.17.1.
- No change to `Bid`, `Award`, `Decision`, `Value` or `Period`.

## 4. Conformance suite changes

- **Codelists.** `eventType.csv` gains `round.opened` and `round.closed` (`auction.opened`, `auction.scheduled` and `bid.placed` already exist). New `bidRejectionReason.csv` and `ineligibilityReason.csv`, both closed. **Binding follows D-39's resolution, whichever shape the Committee adopts** (bare `enum`, or `anyOf: [{enum}, {pattern}]`); this proposal does not pre-empt that decision by choosing a generator shape for them. Both are payload and record vocabularies: `Event.payload` is an open object, so no schema property exists today at which `bindings.json` could bind `bid.rejected`'s `reason`, and the close inputs record's `eligibility[].reason` is bound when D-39's shape is applied to `auction-close-inputs.schema.json`. Until the Committee resolves D-39, the checker validates both against the CSVs (A14, A7), and each CSV header comment states the binding is pending D-39. *(CP decision, §7.1.)*
- **State model.** The Auction entry loses the `open → closed` edge (§2.3.1); the gating in §2.3.1 is encoded so `check-state-model.js` fails a `bid.placed` in `open`.
- **`check-auction.js`**, rules added to A1 to A3:
  - A4 projection replay and close inputs record byte identity;
  - A5 time boundary and chain-time monotonicity;
  - A6 state gating and freezing;
  - A7 eligibility at close;
  - A8 tie resolution, including the seed;
  - A9 currency, precision and `amountMinor` range;
  - A10 supported combination and currency;
  - A11 single lot;
  - A12 `sourcingEvent` present and resolvable to a `SourcingEvent`;
  - A13 chain scope and §2.1 hash;
  - A14 rejection completeness: every invalid placement rejected with the right reason, no valid one rejected, and supersession named correctly.

  A2 stops reading directory order, and Dutch is no longer treated as lower-wins.
- **Fixtures** `conformance/fixtures/auction/<case>/` with `auction.json`, `events.ndjson`, `inputs/` and `expected/{close-inputs.json,decision.json,award.json}`. Cases:
  - `happy-two-round`, `reserve-exact`, `step-exact`, `tie-earliest`, `tie-seeded`, `same-bidder-repeat`, `supersession`, `withdrawal-then-rebid`;
  - `ineligible-best-price`, `ineligible-value-cap`, `none-eligible`;
  - `no-improvement-close`, `max-rounds-close`, `fixed-time-boundary`;
  - `duplicate-replay`, `jpy-zero-exponent`, `precision-breach`, `bid-in-open-state`, `chain-foreign-bid`, `timestamp-regression`;
  - `reserved-tuple-fails`.

  Expected outputs are computed by hand from this text before any runtime is run against them.
- **Vectors** `conformance/vectors/event-hash/` (§2.1), recomputed by a suite test.
- **Reference runtime.** `auction/` and the site's browser twin emit `auction.started`, `round.*`, supersession and the anchored record, and pass every fixture. They receive no exemption.

## 5. Backward compatibility

- **Core.** The `previousEventHash` pattern matches the tooling's output byte for byte, and no tracked file stores a hash. An external store holding hashes in another format would fail validation; none is known.
- **Extension.** Breaking for an Auction using a reserved combination or `random-seeded` without a seed, and for any record relying on `open → closed`. None is certified. `examples/auction-reverse.json` already uses a supported combination and carries `sourcingEvent`.
- **Migration.** None for records. Implementers re-run the checker and the vectors.

## 6. Rejected alternatives

- **A. Change core `Value.amount` to a string decimal.** Declined: breaking across every layer and EN 16931 alignment, to solve a problem the extension solves locally (§2.5).
- **B. Infer rounds from `Bid.round`.** Declined: the no-improvement close depends on a round completing, which a bid cannot express.
- **C. Admit bids strictly before `period.endDate`.** Declined: a second boundary convention in the standard. Either is deterministic; one is kept.
- **D. Seed in `Decision.outcome`.** Declined: untyped, and discoverable only after close.
- **E. Suspend `random-seeded`.** Declined: cheap to rescue.
- **F. Echo the seed and close-record hash into `Decision.inputs`.** Not expressible: `Identifier.scheme` is closed to entity-naming schemes (D-20). The anchored close inputs record carries both (§2.2).
- **G. Reject ineligible bids at placement only.** Declined: loses the audit record when qualification changes between placement and close.
- **H. Void the auction when the best bidder is ineligible.** Declined: punishes every bidder for one bidder's status.
- **I. Require `sourcingEvent` in `auction.schema.json` now.** Deferred, not declined: the Auction primitive also serves non-certified demonstrations, and the global requirement is a larger decision (§7).
- **J. Per-subject chains for Bids.** Declined: the relative order of Bid events across subjects would not be recoverable, and chain position could not be authoritative (D-71).
- **K. Bare lowercase hex for `previousEventHash`.** Declined: changes every runtime's output for no gain, and the prefix names the algorithm for a future change.
- **L. Bundle the full ISO 4217 table.** Declined: an externally maintained list snapshotted into the conformance surface ages silently. The matrix lists supported currencies and grows by amendment.

### 7.2 Questions for the Committee

None blocks adoption of this text:

- **Q-1.** Whether `Auction.sourcingEvent` becomes required in the schema, not only in the profile.
- **Q-2.** A multi-winner award model, which unreserves `split`.
- **Q-3.** The sealed-value mechanism: commitment and reveal, or envelope.
- **Q-4.** A signed or externally anchored close commitment (roadmap, EAE-0002 P2-3).
- **Q-5.** On D-20's resolution, whether the close `Decision` references its anchored close inputs record directly.
- **Q-6.** Seed grinding. A seed published before bidding lets a party able to choose an identity after seeing the seed search for a favourable HMAC output, and so win ties. The exposure is bounded to ties at equal `amountMinor` among eligible standing Bids. Three options, none decided here:
  - **(a) As drafted: seed published with the Auction, from `auction.scheduled`.** Keeps G-4 as decided and is simplest to implement and replay. Cost: the gaming window stays open for as long as a new identity can join after publication.
  - **(b) Committed seed, revealed at close.** `rules` carries a `sha256:` commitment; `auction.closed` reveals the seed, and the checker verifies it against the commitment. Closes the window for every party. Cost: reverses G-4's "published before bidding", because bidders cannot compute the tie-break in advance; it adds a reveal step an operator can fail to perform, which needs its own rule; and the auctioneer, who knows the seed, can still grind.
  - **(c) Freeze the eligible bidder set before seed publication.** Registration closes, then the seed publishes, then bidding runs. The frozen set is recorded on the chain before the seed, for example as an `auction.started` payload member naming the bidder `Identifier`s, and a `bid.placed` from a bidder outside it is rejected. Closes the gaming window without reversing G-4, because the seed is still published before bidding and no identity chosen after publication can bid. Cost: no late registration once the seed is out. The seed would move from `auction.scheduled` to `auction.started`, which is still before `in_progress` bidding.
- **Q-7.** Qualification condition types other than `valueCap`, which §2.3.7 treats as `condition-unsupported`.
- **Q-8.** Whether §2.1's hash definition, which binds every Event chain, should be split into its own core record before adoption.
